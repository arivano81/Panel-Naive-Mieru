# Дорожная карта VertaFlux

Актуально на: 10 ноября 2026 года
Текущая версия: 1.19.0

Этот документ — единый рабочий план развития проекта. Он описывает порядок реализации,
ограничения, критерии готовности и решения, которые не должны приниматься «по ходу» без
проверки безопасности и совместимости.

## 1. Цель проекта

Развить VertaFlux в самостоятельную, безопасную и понятную панель управления несколькими
VPN/proxy-протоколами, сохраняя совместимость действующих установок и исключая скрытые
изменения системы. Каждое изменение проходит миграцию, тестирование, Debian 12/13 CI и
canary; рабочий VPS обновляется только при доказанной изоляции незатронутых служб.

Порядок исполнения цели:

1. завершить переход на VertaFlux через обратимо совместимую dual-read/dual-write миграцию;
2. создать общий контур `измерить → рекомендовать → diff → подтвердить → проверить → применить
   только к выбранной службе → health-check → откатить`;
3. реализовать контур для Hysteria2, Mieru и NaiveProxy/Caddy, затем унифицировать его с Xray;
4. вынести глобальные sysctl, IPv6, DNS и firewall в отдельные явно подтверждаемые операции;
5. добавить историю рекомендаций, изменений и откатов;
6. провести интеграционные и реальные canary-тесты;
7. обновлять рабочий VPS без перезапуска незатронутых VPN-служб.

Управляемые способы подключения:

- NaiveProxy;
- Mieru;
- Hysteria2;
- VLESS на базе Xray-core;
- экспериментальные OpenFlux-профили.

Панель должна устанавливать компоненты, управлять пользователями, выдавать клиентские
конфигурации, считать трафик, применять ограничения, создавать резервные копии и давать
администратору проверяемый итог каждой операции.

## 2. Основные принципы

1. Новые компоненты выключены по умолчанию и устанавливаются только по решению администратора.
2. Обновление не включает новый протокол существующим пользователям автоматически.
3. Перед перезапуском службы новый конфиг проверяется; при ошибке выполняется откат.
4. Секреты не попадают в журналы, API-ответы и диагностические отчёты.
5. Бинарники загружаются из зафиксированного релиза и проверяются по SHA-256.
6. `latest` нельзя использовать в production-установщике без проверки версии проектом.
7. Пользовательские данные и текущие протоколы сохраняются при обновлении.
8. README и CHANGELOG обновляются вместе с пользовательской функцией.
9. Экспериментальные функции визуально отделены от стабильных.
10. Ни один транспорт не объявляется «необнаруживаемым» или гарантированно работающим в любой сети.
11. Перед обновлением любого production-бинарника, способного прервать VPN-службу, оператор
    отдельно подтверждает обновление именно этого компонента непосредственно перед запуском.
    Текущий активный протокол не предполагается заранее: обновления выполняются по одному,
    с фиксацией состояния, проверкой остальных служб и готовым откатом.

### 3.1 Единый контур настройки VPN-служб

Настройки компонентов развиваются по одной безопасной схеме:

`измерить → предложить → показать значения → подтвердить → проверить конфиг → применить → проверить службу → откатить при ошибке`.

- [x] Xray/VLESS: CPU/RAM/load, MTU, IPv6, TCP Fast Open, congestion control, keepalive,
  user timeout, DNS strategy и route-only sniffing;
- [x] Hysteria2: ресурсы VPS и MTU, congestion control, QUIC/UDP timeout, число потоков и
  Path MTU Discovery с сохранением userpass-аутентификации; bandwidth остаётся без лимита,
  пока администратор не измерит реальную пропускную способность;
- [x] Mieru: read-only анализ ресурсов и route MTU, редактируемые MTU, клиентский multiplexing,
  TCP/TCP+UDP bindings и traffic pattern; подтверждённое применение перезапускает только Mieru,
  а при ошибке возвращает предыдущую конфигурацию;
- [x] NaiveProxy/Caddy: read-only анализ ресурсов, редактируемые `dial_timeout`,
  `max_idle_conns` и `max_idle_conns_per_host`; применение не меняет домен, сертификат,
  probe resistance или учётные данные, валидирует кандидат и откатывается при ошибке;
- [x] общий SQLite-журнал рекомендаций и успешных применений, точный diff перед подтверждением
  и единая история для Xray, Hysteria2, Mieru и NaiveProxy/Caddy без секретных значений;
- [x] чистая установка и установщик Hysteria2 больше не применяют глобальные sysctl и не
  отключают IPv6 автоматически; они только показывают read-only рекомендацию;
- [x] dual-read миграция legacy-каталогов в `/etc/vertaflux` и `/var/lib/vertaflux`:
  данные перемещаются без копирования, старые пути остаются совместимыми символическими
  ссылками для helper-скриптов и отката; конфликт каталогов останавливает миграцию без слияния.

Ни один совет не применяется автоматически. Анализ не изменяет sysctl или firewall, а применение
перезапускает только затронутую службу. Для действующих установок новые настройки выключены до
явного решения администратора.

Важно: автоматический Debian 13 canary проверяет закреплённый Xray, генерацию ключей и
production-конфиг. 27 сентября 2026 года внешний Debian 13 VPS также прошёл установку,
systemd/firewall и реальный HTTPS-трафик через официальный Xray-клиент Windows. Вторым
клиентом официальный sing-box 1.14.2 проверил сгенерированный JSON и провёл HTTPS-трафик
через тот же REALITY-профиль. Статистика, общий лимит, WARP/cascade и федерация реализованы;
XHTTP остаётся отдельным последующим профилем.

## 6. Этапы B–D — полноценный VLESS

За сервер отвечает Xray-core. Поддерживаются два отдельных профиля:

1. **VLESS + REALITY + Vision** — первый стабильный профиль.
2. **VLESS + XHTTP + TLS** — следующий профиль через существующий Caddy.

Документация основы:

- [VLESS](https://xtls.github.io/en/config/inbounds/vless.html)
- [REALITY](https://xtls.github.io/en/config/transports/reality.html)
- [транспорты Xray](https://xtls.github.io/en/config/transport.html)

### 6.3 Первый профиль: REALITY

Первый выпуск использует отдельный TCP-порт, например `8443`, чтобы не переносить NaiveProxy
с уже занятого `443/tcp`.

```text
VLESS-клиент
    │
    ▼
Xray :8443/tcp
    │  VLESS + REALITY + xtls-rprx-vision
    ▼
Internet / WARP / Cascade
```

Панель генерирует ключи и `shortId`, валидирует `target`, не возвращает private key обычным
API и предупреждает, что замена ключей отключит существующие клиенты.

27 сентября 2026 года WARP прошёл реальный reboot-canary на Debian 13:
`wg-quick@warp` восстановил туннель после смены boot ID, запрос через
официальный Xray/VLESS-клиент вышел с Cloudflare egress-IP, а SSH и панель
остались доступны. Teardown удалил интерфейс, policy rules и правила панели.
Каскаду ещё требуется отдельная пара Entry/Exit для такого же теста. Репозиторий содержит
guarded-сценарий `tests/cascade-systemd-canary.sh`: он проверяет настоящий VLESS egress до
и после смены boot ID, восстановление systemd/iptables, неизменность основных служб и
разрешает штатную очистку только после успешной post-reboot проверки.
Поставка Mita и лениво устанавливаемого Mieru-клиента закреплена на 3.38.0;
чистая установка, обновление и каскад проверяют SHA-256 до вызова `dpkg`.
Caddy Naive закреплён на `v2.11.7-naive2`; установщик и обновление сверяют архив по
SHA-256 до распаковки и остановки службы; `latest` в этих путях больше не используется.
Hysteria2 закреплена на `app/v2.12.3`: контрольная сумма и `version` smoke-test выполняются
до атомарной замены бинарника; неизвестная архитектура отклоняется. На внешнем Debian 13 VPS
штатный API панели установил Hy2, официальный CLI-клиент провёл HTTP-запрос через UDP/443,
а после смены boot ID сервис и туннель повторно прошли тот же тест. Временные пользователи
и клиентские файлы удалены.

### 6.7 XHTTP

Добавляется после стабилизации REALITY:

Текущий статус: opt-in адаптер генерирует loopback Xray inbound, клиентскую ссылку и
path-scoped Caddy h2c route; реальный pinned-binary canary проверяет объединённый конфиг.
Xray и Caddy применяются одной транзакцией с общим откатом. В панели доступны явное
включение/выключение, отдельная ссылка/QR и условная выдача в подписках. 27 сентября
2026 года эксплуатационный canary на Debian 13 прошёл внешний туннель Xray 26.3.27 и
независимый туннель Mihomo 1.19.31; неверный path отклонён Caddy с `403`, а очистка
вернула Caddyfile, Xray, Mita и конфиг панели к исходным SHA-256.

```text
VLESS-клиент
    │ XHTTP + TLS
    ▼
Caddy :443 ── секретный path ──▶ Xray 127.0.0.1:<порт> ──▶ Internet
```

Приёмочная матрица XHTTP: Xray 26.3.27 (Windows, внешний клиент) и Mihomo 1.19.31
(Linux amd64, отдельная реализация транспорта). gRPC не является основным новым профилем;
он может остаться только как совместимый дополнительный вариант.

## 7. Этап E — OpenFlux Experimental MVP

OpenFlux — отдельная подсистема, а не четвёртый флажок общего пользователя. Причина: один
защищённый negotiated exit обслуживает одну активную клиентскую сессию. Поэтому применяется
модель независимых профилей.

Источник: [p1neappleXpress/OpenFlux](https://github.com/p1neappleXpress/OpenFlux)

Лицензия внешнего компонента: GPL-3.0

Текущая проверяемая версия: v0.17.1

### 7.0 Изоляция от основного проекта

Это обязательное условие интеграции, имеющее приоритет над скоростью разработки:

- OpenFlux реализуется отдельным модулем и не встраивается в генераторы Caddy, Mieru, Hy2 или Xray;
- модуль имеет собственные API-маршруты `/api/openflux/*`, хранилище, scripts и systemd-unit;
- при `openflux.enabled=false` результат генерации всех существующих конфигов должен быть
  байт-в-байт таким же, как до добавления модуля;
- обычная установка и обычное обновление не скачивают OpenFlux, не создают его пользователя,
  не открывают порты и не меняют firewall;
- ошибка, зависание или падение OpenFlux не влияет на health-check основного proxy stack;
- перезапуск OpenFlux никогда не перезапускает Caddy, Mieru, Hy2, Xray или панель;
- удаление OpenFlux не вызывает общий `update.sh --repair` и не перестраивает чужие конфиги;
- модуль не получает доступ к SQLite с пользовательскими паролями;
- OpenFlux-профили не добавляются в общий массив `protocols` и не участвуют в Sub-ссылках MVP;
- firewall-правила OpenFlux маркируются, учитываются по профилям и удаляются только по своей метке;
- OpenFlux не меняет default route, policy routing, WARP или cascade в MVP;
- все пути и имена служб имеют префикс `openflux`, чтобы избежать пересечений.

Интеграция выполняется в три внутренних стадии:

1. **Adapter only** ✅ — генератор L4/Direct exit/client-конфигов и unit-файла тестируется
   без установки и запуска бинарника; основной сервер его не импортирует.
2. **Isolated canary** ✅ — opt-in установщик подготавливает проверенный бинарник без запуска
   и firewall; CI поднимает одноразовый encrypted L4/Direct туннель и отвергает неверный
   ключ. Изолированный CLI уже реализует create/start/stop/restart/status/remove с
   per-profile key и firewall rollback. Mock-systemd/UFW fault-тест проверяет failed-start
   rollback, отказ до изменения службы при занятом порте или повреждённом config, bounded
   timeout зависшего systemd и полный lifecycle в изолированном `/tmp` root. Для отдельного
   Debian 13 подготовлен guarded трёхфазный systemd/reboot/uninstall canary. 27 сентября
   2026 года внешний прогон завершён: encrypted L4/Direct tunnel прошёл, неверный ключ
   отклонён, профиль восстановился после реальной перезагрузки, scoped uninstall вернул
   исходные хэши основных конфигов, firewall и состояния служб.
3. **Opt-in UI** — закрытый admin API и отдельная экспериментальная страница уже
   предоставляют install/list/create/start/stop/restart/remove без выдачи ключа. Безопасный
   журнал, подтверждаемый экспорт bundle и транзакционная ротация ключа реализованы. Проект
   переведён на checksum-pinned `v0.17.1`; его прежний INI-формат L4/Direct сохранён upstream.
   Перед признанием версии рабочей обязательный Debian 13 CI-canary должен поднять одноразовый
   зашифрованный туннель, провести трафик и отвергнуть неверный ключ. Отдельный VPS-стенд не
   создаётся: OpenFlux не использовался в production и не имеет действующих клиентов.

До третьей стадии README не должен предлагать OpenFlux как стабильный пользовательский протокол.

### 7.1 Границы MVP

- функция выключена по умолчанию;
- exit только в режиме `l4` на базе gVisor;
- только транспорт `Direct`;
- обязательны `--encryption-key-file` и `--negotiate`;
- один профиль = один ключ = один клиент = один systemd-сервис;
- Android и CLI как первые поддерживаемые клиенты;
- OpenFlux не входит в стандартную Sub-ссылку;
- WARP, каскад и L3 не входят в MVP;
- токены сторонних платформ и CAPTCHA не обрабатываются панелью.

### 7.2 Размещение

```text
/usr/local/bin/openflux
/etc/openflux/profiles/<id>.conf
/etc/openflux/secrets/<id>.key
/etc/systemd/system/openflux-exit@.service
/var/log/openflux/
```

OpenFlux запускается как отдельный внешний бинарник. Его исходный код не копируется и не
связывается с кодом панели. В дистрибутиве сохраняются лицензия, NOTICE, версия и ссылка на
соответствующий исходный код.

### 7.3 Установщик

- скачать конкретный release asset для поддерживаемой архитектуры;
- сверить SHA-256 с доверенным списком в репозитории панели;
- отказаться от установки при несовпадении;
- создать отдельного системного пользователя `openflux`;
- использовать минимальные systemd-права;
- открыть только порт выбранного Direct-профиля;
- обновлять атомарно с возможностью отката;
- не загружать `latest` автоматически.

### 7.4 Интерфейс

Backend-основа реализована в отдельном namespace `/api/openflux/*`; все маршруты требуют
администраторскую сессию, используют allowlist действий и вызывают только изолированный CLI.
Установка не создаёт профиль и ничего не запускает. Начальная отдельная страница реализована;
QR/ссылка берутся только из официального формата `openflux://` v0.17.1; панель не генерирует
собственный несовместимый формат. Их включение остаётся отдельной задачей после прохождения
binary-canary. Экспорт bundle и ротация требуют повторного ввода пароля,
ограничен отдельным rate limit и отдаётся с `Cache-Control: no-store`. Журнал ограничен конкретным
instance-unit, числом строк и фильтром потенциальных секретов.

Отдельная страница **OpenFlux Experimental**:

- установленная и доступная версия;
- предупреждение об экспериментальном статусе;
- список профилей;
- создание имени, порта и ключа;
- запуск, остановка, перезапуск и удаление;
- состояние `openflux-exit@<id>.service`;
- последние безопасно отфильтрованные строки журнала;
- QR и `openflux://`-ссылка;
- ротация ключа с предупреждением об отключении старого клиента;
- проверка доступности порта и соединения.

### 7.5 Секреты

- ключ генерируется из криптографически стойкого источника;
- минимальная длина соответствует требованиям OpenFlux;
- ключ хранится отдельным файлом `600`;
- API возвращает его только при создании или явной ротации;
- ключ, tokens, cookies и полный share-link маскируются в логах;
- экспорт OpenFlux-секретов требует отдельного подтверждения администратора.

### Критерии готовности MVP

- полный существующий набор тестов проходит до и после добавления модуля;
- [x] golden-тест подтверждает байт-в-байт неизменность Caddyfile, Mieru, Hy2, Xray и подписок
  при выключенном модуле и отсутствие OpenFlux-веток в основных генераторах;
- [x] install, update, start, stop, reset и uninstall OpenFlux идемпотентны
  (точный install/update завершается до сети; reset и архивируемый uninstall покрыты Linux fixture);
- [x] fault-тесты покрывают оборванную/недоступную загрузку, неправильный SHA-256, занятый порт,
  повреждённый config, неудачный и зависший старт systemd;
- [x] каждый сбой оставляет основные службы активными и исходные firewall-правила неизменными;
- [x] два профиля могут работать одновременно на разных портах — покрыто Linux lifecycle fixture;
- [x] один профиль не читает ключ другого — fixture проверяет разные mode-600 ключи и независимое удаление;
- [x] перезапуск сервера восстанавливает включённые профили — instance units сохраняются enabled,
  а отдельный Debian 13 canary проверяет состояние после реальной перезагрузки;
- [x] неправильный ключ не приводит к незашифрованному fallback — реальный binary canary требует отказ;
- [x] удаление профиля закрывает только его порт и удаляет только его секрет;
- [x] Naive, Mieru, Hy2 и VLESS продолжают работать;
- [x] лицензия и версия внешнего компонента отображаются в UI и документации.

## 8. Этап G — OpenFlux v0.17.1 и дополнительные транспорты

Сначала подтверждается уже изолированный L4/Direct путь на закреплённом бинарнике v0.17.1.
Canary запускается в одноразовом окружении Debian 13 и не обращается к production-серверу,
его firewall или работающим Naive, Mieru, Hysteria2 и Xray. До зелёного canary OpenFlux
остаётся выключенным по умолчанию и не предлагается как готовый клиентский протокол.

Транспорты добавляются по одному после отдельного аудита:

1. Yandex Docs/Volga/Board;
2. Mail.ru Docs;
3. Cups.online;
4. MAX/OneMe;
5. multi-transport failover.

Для каждого транспорта отдельно проверяются правила сторонней платформы, формат credentials,
срок жизни cookies, утечки через журнал, восстановление после CAPTCHA и поведение при блокировке
аккаунта. Панель не должна автоматически решать CAPTCHA или передавать cookies без явного
действия администратора.

L3 не включается, пока не будут готовы изолированный network namespace, scoped RST-rule,
автоматическая очистка firewall и тесты восстановления SSH-доступа.

## 9. Общая безопасность

- [x] CSRF-защита всех аутентифицированных изменяющих API session-bound токеном;
- [x] ротация session ID после входа и смены пароля с выдачей нового CSRF-токена;
- [x] опциональный TOTP администратора с QR-настройкой, защитой от replay и recovery-сбросом;
- [x] аудит изменяющих действий администратора в SQLite без тел запросов и секретов;
- [x] отдельные rate limit для login, публичных подписок и всех федеративных операций;
- [x] маскирование паролей, UUID, tokens, private keys и subscription URL в runtime/access/install логах;
- [x] шифруемый backup: AES-256-GCM, `scrypt`, отдельная парольная фраза, повторная
  проверка пароля администратора, rate limit и импорт прежних JSON без возможности
  нового plaintext-экспорта;
- [x] logrotate и лимиты файловых журналов панели, установщика и cascade-watchdog;
- [x] npm audit для production-зависимостей с CI-блокировкой от moderate и выше;
- [ ] проверка Go-зависимостей внешних компонентов: еженедельный и ручной
  `govulncheck -mode binary` скачивает exact checksum-pinned amd64 assets Caddy,
  Mita/Mieru, Hysteria2, Xray, wgcf и OpenFlux, сохраняет отчёты и падает при

  production-запуск выявил findings во всех семи бинарниках; пункт останется

  либо документированного VEX по каждому конкретному finding. Manifest теперь
  также закрепляет полный upstream commit, а второй source-mode проход строит
  call graph всех Go modules для обоснованного VEX. Контрольный запуск 10 ноября
  2026 года повторно подтвердил блокер; artifact теперь получает автоматическую
  Markdown/JSON-сводку уникальных advisory без их подавления. После перехода на Caddy

- [ ] собственные воспроизводимые security-сборки Caddy, Mieru, Hysteria2,
  Xray, wgcf и OpenFlux перенесены в ветку 2.0/3.0. Линейка 1.x использует

- [x] keyless Sigstore-подпись release artifacts через OIDC GitHub Actions: archive,

- [x] security contact через private GitHub Security Advisory и документированная процедура отзыва релиза.

## 10. Эксплуатация и удобство

### 10.1 Порядок обновления VPN-компонентов

1. Проверить релиз, исходный commit, SHA-256, changelog и совместимость конфигурации в CI.
2. Подготовить backup, rollback и проверки PID/health всех VPN-служб.
3. Непосредственно перед production-обновлением сообщить, какую службу оно может прервать,
   и получить отдельное подтверждение оператора именно для этого бинарника.
4. Обновлять только один компонент за раз; остальные службы и их конфиги не менять.
5. После обновления проверить версию, конфиг, порт, реальный трафик и неизменность остальных PID.
6. Следующий VPN-компонент не обновлять до отдельной команды оператора.

Правило относится ко всем VPN-компонентам, включая Naive/Caddy, Mieru/Mita, Hysteria2,
Xray/VLESS и OpenFlux. Исключение допустимо только для доказанного no-op без замены бинарника,
перезапуска службы или изменения активного профиля.

- [x] мастер первого запуска после установки: показывает назначение протоколов,
  проверяет три адреса и напоминает о TOTP/зашифрованном backup, но не включает
  дополнительные компоненты без решения администратора;
- [x] единая страница здоровья всех компонентов;
- [x] безопасное обновление только UI/API через `update.sh --panel-only` без
  перезапуска Caddy/Naive, Mieru, Hy2 или Xray и с проверкой их PID;
- [x] понятные сообщения вместо необработанного stdout: каскад и WARP показывают
  классифицированный итог, а сырой вывод доступен только в закрытом блоке
  технических подробностей;
- [x] экспорт диагностического отчёта без секретов: единый allowlist-collector не
  возвращает raw config/log stdout, сводит пользователей к количеству и формирует
  versioned JSON с `no-store`;
- [x] уведомление о доступной версии без автоматического обновления: read-only API
  сравнивает локальный `VERSION` с приватной веткой `main`, кэширует результат и не хранит токен;
- [x] новые установки и создаваемые артефакты используют только имя VertaFlux; старые пути,
  backup tags и browser keys читаются исключительно как совместимость для миграции и импорта;
- [x] maintenance mode блокирует изменяющие административные API без остановки VPN-служб;
  status, диагностика, зашифрованный backup и выключение режима остаются доступны;
- [x] проверенный root-only backup автоматически создаётся перед изменением портов,
  ключей и доменов; при ошибке записи операция блокируется до изменения состояния;
- [x] read-only диагностика проверяет публичные A/AAAA-записи основного, panel- и
  sub-доменов, совпадение с IP сервера, имя и срок действия TLS-сертификатов;
- [x] отдельный раздел панели классифицирует Karing, Shadowrocket, sing-box,
  NekoBox/Exclave/Throne, Xray, Mihomo, официальные CLI и OpenFlux по уровню проверки;
- [x] русская и английская документация описывает каждую стабильную функцию, границы
  экспериментального OpenFlux и безопасные эксплуатационные процедуры.
