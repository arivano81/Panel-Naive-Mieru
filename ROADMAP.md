# Дорожная карта Panel Naive Mieru

Актуально на: 26 сентября 2026 года
Текущая версия: 1.12.0

Этот документ — единый рабочий план развития проекта. Он описывает порядок реализации,
ограничения, критерии готовности и решения, которые не должны приниматься «по ходу» без
проверки безопасности и совместимости.

## 1. Цель проекта

Сделать понятную администратору панель для управления несколькими независимыми способами
подключения к личному серверу:

- NaiveProxy;
- Mieru;
- Hysteria2;
- VLESS на базе Xray-core;
- экспериментальные OpenFlux-профили.

Панель должна устанавливать компоненты, управлять пользователями, выдавать клиентские
конфигурации, считать трафик, применять ограничения, создавать резервные копии и давать
администратору проверяемый итог каждой операции.

## 2. Основные принципы

1. Новые компоненты выключены по умолчанию и устанавливаются только по решению администратора.
2. Обновление не включает новый протокол существующим пользователям автоматически.
3. Перед перезапуском службы новый конфиг проверяется; при ошибке выполняется откат.
4. Секреты не попадают в журналы, API-ответы и диагностические отчёты.
5. Бинарники загружаются из зафиксированного релиза и проверяются по SHA-256.
6. `latest` нельзя использовать в production-установщике без проверки версии проектом.
7. Пользовательские данные и текущие протоколы сохраняются при обновлении.
8. README и CHANGELOG обновляются вместе с пользовательской функцией.
9. Экспериментальные функции визуально отделены от стабильных.
10. Ни один транспорт не объявляется «необнаруживаемым» или гарантированно работающим в любой сети.

## 6. Этапы B–D — полноценный VLESS

1. **VLESS + REALITY + Vision** — первый стабильный профиль.

### 6.3 Первый профиль: REALITY

Первый выпуск использует отдельный TCP-порт, например `8443`, чтобы не переносить NaiveProxy
с уже занятого `443/tcp`.

```text
VLESS-клиент
    │
    ▼
Xray :8443/tcp
    │  VLESS + REALITY + xtls-rprx-vision
    ▼
Internet / WARP / Cascade
```

Панель генерирует ключи и `shortId`, валидирует `target`, не возвращает private key обычным
API и предупреждает, что замена ключей отключит существующие клиенты.

### 6.7 XHTTP

Добавляется после стабилизации REALITY:

Текущий статус: opt-in адаптер генерирует loopback Xray inbound, клиентскую ссылку и
path-scoped Caddy h2c route; реальный pinned-binary canary проверяет объединённый конфиг.
Xray и Caddy применяются одной транзакцией с общим откатом. В панели доступны явное
включение/выключение, отдельная ссылка/QR и условная выдача в подписках. До завершения
этапа остаётся внешняя клиентская матрица и эксплуатационный canary.

```text
VLESS-клиент
    │ XHTTP + TLS
    ▼
Caddy :443 ── секретный path ──▶ Xray 127.0.0.1:<порт> ──▶ Internet
```

До релиза обязательна отдельная матрица совместимости клиентов. gRPC не является основным
новым профилем; он может остаться только как совместимый дополнительный вариант.

### Критерии готовности VLESS

- установка, переустановка и удаление не затрагивают Naive/Mieru/Hy2;
- CRUD одного пользователя не отключает остальных;
- невалидный конфиг не попадает в production;
- ссылки работают минимум в двух поддерживаемых клиентах;
- сроки, квоты и статистика проверены интеграционными тестами;
- WARP и каскад проходят тест после перезагрузки;
- backup/restore сохраняет UUID и настройки сервера;
- README содержит установку, использование и диагностику.

## 7. Этап E — OpenFlux Experimental MVP

OpenFlux — отдельная подсистема, а не четвёртый флажок общего пользователя. Причина: один
защищённый negotiated exit обслуживает одну активную клиентскую сессию. Поэтому применяется
модель независимых профилей.

Источник: [p1neappleXpress/OpenFlux](https://github.com/p1neappleXpress/OpenFlux)

Лицензия внешнего компонента: GPL-3.0

Первая проверяемая версия: 0.0.5

### 7.0 Изоляция от основного проекта

Это обязательное условие интеграции, имеющее приоритет над скоростью разработки:

- OpenFlux реализуется отдельным модулем и не встраивается в генераторы Caddy, Mieru, Hy2 или Xray;
- модуль имеет собственные API-маршруты `/api/openflux/*`, хранилище, scripts и systemd-unit;
- при `openflux.enabled=false` результат генерации всех существующих конфигов должен быть
  байт-в-байт таким же, как до добавления модуля;
- обычная установка и обычное обновление не скачивают OpenFlux, не создают его пользователя,
  не открывают порты и не меняют firewall;
- ошибка, зависание или падение OpenFlux не влияет на health-check основного proxy stack;
- перезапуск OpenFlux никогда не перезапускает Caddy, Mieru, Hy2, Xray или панель;
- удаление OpenFlux не вызывает общий `update.sh --repair` и не перестраивает чужие конфиги;
- модуль не получает доступ к SQLite с пользовательскими паролями;
- OpenFlux-профили не добавляются в общий массив `protocols` и не участвуют в Sub-ссылках MVP;
- firewall-правила OpenFlux маркируются, учитываются по профилям и удаляются только по своей метке;
- OpenFlux не меняет default route, policy routing, WARP или cascade в MVP;
- все пути и имена служб имеют префикс `openflux`, чтобы избежать пересечений.

Интеграция выполняется в три внутренних стадии:

1. **Adapter only** ✅ — генератор L4/Direct exit/client-конфигов и unit-файла тестируется
   без установки и запуска бинарника; основной сервер его не импортирует.
2. **Isolated canary** ✅ — opt-in установщик подготавливает проверенный бинарник без запуска
   и firewall; CI поднимает одноразовый encrypted L4/Direct туннель и отвергает неверный
   ключ. Изолированный CLI уже реализует create/start/stop/restart/status/remove с
   per-profile key и firewall rollback. Mock-systemd/UFW fault-тест проверяет failed-start
   rollback, отказ до изменения службы при занятом порте или повреждённом config, bounded
   timeout зависшего systemd и полный lifecycle в изолированном `/tmp` root. Для отдельного
   Debian 13 подготовлен guarded трёхфазный systemd/reboot/uninstall canary; остаётся
   зафиксировать его внешний прогон.
3. **Opt-in UI** — закрытый admin API и отдельная экспериментальная страница уже
   предоставляют install/list/create/start/stop/restart/remove без выдачи ключа. До полного
   UI остаются QR/ссылка; безопасный журнал, подтверждаемый экспорт bundle и транзакционная
   ротация ключа уже реализованы. QR нельзя выпускать на закреплённом `0.0.5`: официальный
   tag ещё не содержит `--share`/пакет `share`; поддержка ждёт следующего проверяемого релиза.

До третьей стадии README не должен предлагать OpenFlux как стабильный пользовательский протокол.

### 7.1 Границы MVP

- функция выключена по умолчанию;
- exit только в режиме `l4` на базе gVisor;
- только транспорт `Direct`;
- обязательны `--encryption-key-file` и `--negotiate`;
- один профиль = один ключ = один клиент = один systemd-сервис;
- Android и CLI как первые поддерживаемые клиенты;
- OpenFlux не входит в стандартную Sub-ссылку;
- WARP, каскад и L3 не входят в MVP;
- токены сторонних платформ и CAPTCHA не обрабатываются панелью.

### 7.2 Размещение

```text
/usr/local/bin/openflux
/etc/openflux/profiles/<id>.conf
/etc/openflux/secrets/<id>.key
/etc/systemd/system/openflux-exit@.service
/var/log/openflux/
```

OpenFlux запускается как отдельный внешний бинарник. Его исходный код не копируется и не
связывается с кодом панели. В дистрибутиве сохраняются лицензия, NOTICE, версия и ссылка на
соответствующий исходный код.

### 7.3 Установщик

- скачать конкретный release asset для поддерживаемой архитектуры;
- сверить SHA-256 с доверенным списком в репозитории панели;
- отказаться от установки при несовпадении;
- создать отдельного системного пользователя `openflux`;
- использовать минимальные systemd-права;
- открыть только порт выбранного Direct-профиля;
- обновлять атомарно с возможностью отката;
- не загружать `latest` автоматически.

### 7.4 Интерфейс

Backend-основа реализована в отдельном namespace `/api/openflux/*`; все маршруты требуют
администраторскую сессию, используют allowlist действий и вызывают только изолированный CLI.
Установка не создаёт профиль и ничего не запускает. Начальная отдельная страница реализована;
QR/ссылка отложены до официального релиза OpenFlux с документированным форматом `openflux://`;
панель не генерирует несовместимый собственный формат. Экспорт bundle и ротация требуют повторного ввода пароля,
ограничен отдельным rate limit и отдаётся с `Cache-Control: no-store`. Журнал ограничен конкретным
instance-unit, числом строк и фильтром потенциальных секретов.

Отдельная страница **OpenFlux Experimental**:

- установленная и доступная версия;
- предупреждение об экспериментальном статусе;
- список профилей;
- создание имени, порта и ключа;
- запуск, остановка, перезапуск и удаление;
- состояние `openflux-exit@<id>.service`;
- последние безопасно отфильтрованные строки журнала;
- QR и `openflux://`-ссылка;
- ротация ключа с предупреждением об отключении старого клиента;
- проверка доступности порта и соединения.

### 7.5 Секреты

- ключ генерируется из криптографически стойкого источника;
- минимальная длина соответствует требованиям OpenFlux;
- ключ хранится отдельным файлом `600`;
- API возвращает его только при создании или явной ротации;
- ключ, tokens, cookies и полный share-link маскируются в логах;
- экспорт OpenFlux-секретов требует отдельного подтверждения администратора.

### Критерии готовности MVP

- полный существующий набор тестов проходит до и после добавления модуля;
- [x] golden-тест подтверждает байт-в-байт неизменность Caddyfile, Mieru, Hy2, Xray и подписок
  при выключенном модуле и отсутствие OpenFlux-веток в основных генераторах;
- install, update, start, stop, reset и uninstall OpenFlux идемпотентны
  (точный install/update завершается до сети; reset и архивируемый uninstall покрыты Linux fixture);
- fault-тесты покрывают оборванную/недоступную загрузку, неправильный SHA-256, занятый порт,
  повреждённый config, неудачный и зависший старт systemd;
- каждый сбой оставляет основные службы активными и исходные firewall-правила неизменными;
- [x] два профиля могут работать одновременно на разных портах — покрыто Linux lifecycle fixture;
- [x] один профиль не читает ключ другого — fixture проверяет разные mode-600 ключи и независимое удаление;
- [x] перезапуск сервера восстанавливает включённые профили — instance units сохраняются enabled,
  а отдельный Debian 13 canary проверяет состояние после реальной перезагрузки;
- [x] неправильный ключ не приводит к незашифрованному fallback — реальный binary canary требует отказ;
- [x] удаление профиля закрывает только его порт и удаляет только его секрет;
- Naive, Mieru, Hy2 и VLESS продолжают работать;
- лицензия и версия внешнего компонента отображаются в UI и документации.

- [x] ротация session ID после входа и смены пароля с выдачей нового CSRF-токена;
- [x] опциональный TOTP администратора с QR-настройкой, защитой от replay и recovery-сбросом;
- [x] аудит изменяющих действий администратора в SQLite без тел запросов и секретов;
- [x] отдельные rate limit для login, публичных подписок и всех федеративных операций;
- маскирование паролей, UUID, tokens и private keys;
- шифруемый backup;
- [x] logrotate и лимиты файловых журналов панели, установщика и cascade-watchdog;
- проверка npm и Go-зависимостей;
- SBOM для релиза;
- подпись release artifacts;
- документированный security contact и процедура отзыва релиза.

## 10. Эксплуатация и удобство

- мастер первого запуска после установки;
- единая страница здоровья всех компонентов;
- понятные сообщения вместо необработанного stdout;
- экспорт диагностического отчёта без секретов;
- уведомление о доступной версии без автоматического обновления;
- maintenance mode на время опасных операций;
- резервное копирование перед изменением портов, ключей и доменов;
- автоматическая проверка DNS и TLS;
- раздел совместимости клиентских приложений;
- русская и английская документация для каждой стабильной функции.

## 11. Правило работы с этапами

Для каждого этапа создаётся короткая спецификация:

1. пользовательский сценарий;
2. изменения данных и конфигов;
3. модель угроз;
4. план миграции;
5. план отката;
6. автоматические тесты;
7. ручные проверки на чистом Debian 13;
8. изменения README и CHANGELOG.

Этап считается завершённым только после выполнения критериев готовности, а не после появления
кнопки в интерфейсе.
