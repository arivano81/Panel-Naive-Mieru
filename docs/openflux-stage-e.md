# OpenFlux Experimental — спецификация этапа E

## Статус

Первая внутренняя стадия: **Adapter only**. На этом этапе OpenFlux нельзя установить или
запустить из панели. Обычные `install.sh` и `update.sh` его не скачивают и не меняют firewall.

Проверяемая внешняя версия: OpenFlux `0.0.5`, лицензия GPL-3.0-or-later. Панель не включает
исходный код OpenFlux и хранит только сведения о релизе, ожидаемый SHA-256 и генераторы
собственных конфигурационных файлов.

## Пользовательский сценарий MVP

Администратор явно устанавливает экспериментальный компонент, создаёт независимый профиль
с именем и непривилегированным TCP-портом, получает отдельный ключ и клиентский конфиг.
Один профиль обслуживает одну активную клиентскую сессию. Профиль не является пользователем
Naive/Mieru/Hy2/VLESS и не попадает в обычную Sub-ссылку.

## Граница первой стадии

Чистый адаптер формирует:

- exit-конфиг только для `Mode = l4`, batched codec и транспорта Direct;
- парный CLI/SOCKS5 client-конфиг;
- hardened-шаблон `openflux-exit@.service` без root-capabilities;
- фиксированные namespaced-пути профиля и его ключа.

Адаптер не читает и не пишет файлы, не запускает команды и не импортируется основным сервером.
Профильный идентификатор строго ограничен, поэтому не может выйти из `/etc/openflux` или
подменить имя systemd-службы.

## Модель угроз

- Незашифрованный fallback запрещён: каждый конфиг требует отдельный key file, а секция
  Direct переводит OpenFlux в negotiated session.
- Path traversal блокируется allowlist-форматом идентификатора.
- Порт ниже 1024 запрещён; OpenFlux работает от отдельного непривилегированного пользователя.
- Ключ не включается в конфиг, unit или журнал — в них находится только путь к файлу.
- Exit и клиент используют одинаковый непубличный encryption context, привязанный к профилю.
- Unit не вызывает shell и не содержит ссылок на службы основного proxy stack.

## Миграция и откат

На стадии Adapter only миграции нет: существующие конфиги, БД, службы и firewall не меняются.
Откат равен удалению новых исходных файлов. Следующая стадия должна получить собственный
атомарный lifecycle и отдельные fault-тесты до появления API или кнопки в UI.

## Автоматические проверки

- соответствие версии, asset и SHA-256 опубликованному релизу `0.0.5`;
- строгая валидация id, порта и публичного host;
- L4/Direct/encryption-инварианты обоих конфигов;
- hardening и изоляция unit-шаблона;
- отсутствие импорта адаптера в сервер, обычный установщик и updater.

## Вторая стадия: безопасная подготовка canary

Внутренний `panel/scripts/install_openflux.sh` устанавливает только закреплённый бинарник,
каталоги и unit-шаблон. Он сверяет SHA-256 до первой системной записи, выполняет identity
smoke-test и сохраняет root-only отчёт. Скрипт намеренно не создаёт профиль, не открывает
порт, не включает и не запускает службу. Обычная установка панели его не вызывает.

## Следующая проверка

Автоматический isolated canary на Debian 13 скачивает тот же закреплённый asset, повторно
проверяет SHA-256, запускает временные L4/Direct exit и SOCKS5 client и выполняет HTTP-запрос
сквозь зашифрованный туннель. Второй клиент с другим ключом не должен получить доступ — это
проверяет отсутствие незашифрованного fallback. Все процессы и файлы существуют только в
одноразовом каталоге CI; systemd и firewall не меняются.

До API и UI остаётся ручной canary с systemd lifecycle, перезагрузкой и полным удалением на
отдельном Debian 13.

## Изолированный lifecycle профиля

Внутренний root-only CLI `panel/scripts/openflux_profile.sh` реализует операции:

```text
create <id> <port> <public-host>
start <id>
stop <id>
restart <id>
status <id>
remove <id>
```

`create` проверяет id, порт и host через общий адаптер, не допускает занятого или уже
назначенного порта, создаёт отдельный ключ и root-only клиентский bundle. Профиль после
создания остановлен, и порт закрыт. `start` добавляет помеченное UFW-правило только этого
профиля, включает его instance-unit для восстановления после перезагрузки и откатывает оба
действия при неудачном health-check. `stop` симметрично выключает instance и удаляет его
правило. `remove` сначала останавливает профиль, затем удаляет его config, metadata, key и
клиентский bundle; другие профили и службы панели не затрагиваются.

Операции сериализованы отдельным lock-файлом. Linux CI запускает lifecycle в выделенном
`/tmp` test-root с mock-systemd/UFW: проверяет create, отказ systemd, симметричный firewall
rollback, успешные start/stop и полное удаление выбранного секрета и bundle. Test-root
жёстко ограничен отдельным подкаталогом `/tmp` и не может направить mock-режим на production.

CLI не импортирован сервером и пока не является пользовательской функцией: перед API/UI
остаётся ручной reboot canary на отдельном Debian 13.
