# VLESS XHTTP через Caddy — спецификация этапа F

## Текущая стадия

Opt-in профиль доступен администратору в Settings. Панель включает его одной транзакцией,
выдаёт отдельную ссылку/QR и добавляет узел в подписки только на время работы профиля.
Действующий VLESS REALITY остаётся независимым и не меняется, когда XHTTP выключен.

## Архитектура

```text
VLESS-клиент
    │ XHTTP + TLS :443
    ▼
Caddy (основной домен, секретный path)
    │ unbuffered h2c, loopback only
    ▼
Xray 127.0.0.1:<xhttpPort>
    │ VLESS + XHTTP mode=auto
    ▼
Internet / WARP / Cascade
```

TLS завершается в существующем Caddy. Xray слушает только loopback и не получает отдельный
публичный firewall-порт. Caddy сопоставляет длинный случайный path и передаёт только его в
Xray по h2c с отключённой буферизацией; остальные запросы продолжают попадать на fake site.

## Инварианты адаптера

- XHTTP включается только явным `enabled=true`;
- loopback-порт — 1024–65535 и не может совпадать со Stats API `10085`;
- host обязан быть DNS-именем для TLS Caddy;
- path начинается с `/`, содержит 16–96 безопасных символов и не допускает traversal;
- XHTTP-клиент не наследует REALITY-only flow `xtls-rprx-vision`;
- ссылка использует `type=xhttp`, `security=tls`, `mode=auto` и HTTPS-порт 443;
- выключенный профиль не добавляет inbound и не меняет REALITY-конфиг.

## Транзакционное применение

При включённом профиле панель сначала записывает временные кандидаты Xray и Caddy и проверяет
оба до изменения работающей системы. Затем Xray запускается первым, Caddy — вторым. Если запись,
запуск или health-check любого компонента завершается ошибкой, восстанавливаются оба исходных
файла, после чего прежние Caddy и Xray применяются в обратном порядке. Резервные копии остаются
рядом с конфигурациями как `.last-good`.

Миграция схемы 8 только добавляет выключенный флаг `stack.vlessXhttp=false`, loopback-порт
`10443` и пустые host/path. Поэтому обновление существующей установки само по себе не меняет
Caddyfile, не открывает порт и не перезапускает новый профиль.

## Проверки перед включением

Debian 13 CI валидирует объединённый REALITY + XHTTP конфиг настоящим закреплённым
Xray `v26.3.27`. Автотесты проверяют общий откат и побайтовую неизменность Caddyfile при
выключенном XHTTP. Панель предоставляет явный API/UI opt-in, безопасную генерацию path,
отдельную ссылку пользователя и условное добавление в обе подписки.

Эксплуатационный gate закрыт 27 сентября 2026 года на Debian 13:

- официальный Xray 26.3.27 на Windows провёл внешний HTTP-запрос через TLS/XHTTP/Caddy;
- официальный Mihomo 1.19.31 (`linux-amd64-compatible`, SHA-256 из GitHub Release API)
  принял `mode=auto` и провёл тот же запрос через независимую реализацию XHTTP;
- публичный egress в обоих случаях совпал с адресом VPS;
- неправильный секретный path получил `403 Forbidden` и не попал в Xray;
- после удаления canary-пользователя и выключения XHTTP SHA-256 Caddyfile, Xray-конфига,
  Mita state и конфигурации панели совпали с исходными; `--doctor` завершился 12/12.

Основа конфигурации: официальные материалы Xray и пример Xray-examples для XHTTP через
Caddy/h2c. XHTTP не описывается как гарантированно необнаруживаемый транспорт.
